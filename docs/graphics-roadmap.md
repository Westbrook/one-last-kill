# Graphics quality task series

This plan began with the actual Three.js 0.185.1 game inspected on August 29, 2026, and includes the August 30 follow-up cycles. The goal is clearer, more convincing materials, silhouettes and motion while preserving responsive combat. More triangles or a newer graphics API are means, not acceptance criteria.

## Decisions on the proposed options

| Option | Decision for this architecture | Reason |
| --- | --- | --- |
| GPT Image 2 textures | Use selectively as offline asset authoring, with an acceptance gate | A generated facial-albedo trial improved the reviewed character heads. Licensed matching PBR triplets proved more productive for repeating walls than further edits of generated brick. Generated color remains distinct from calibrated material data. |
| More polygons | Spend on close silhouettes, furniture construction, grips and deformation | The August 29 review recorded 8,388 triangles for fists and about 13.4–14.8k in four body draws for NPCs; these are historical asset counts. Further allocation follows visible defects rather than adding subdivisions everywhere. |
| WebGL → WebGPU | Prototype later; do not make it a prerequisite | August 29 combat runs reached the reference display's roughly 120 FPS cadence. This game uses a WebGL GTAO/OutputPass pipeline; migration requires a different post-processing implementation and cross-browser validation. Those earlier runs do not certify the current build. |
| Review and polish | Highest continuing priority | Compare fixed camera views, moving encounters, close-ups and quality modes. Revisit the weakest remaining element after each accepted pass. |
| Other investments | Asset-specific finishes, physical UVs, batching, shader warmup, lighting, LOD and honest profiling | These improve visible quality or free the frame budget needed to support it. |

OpenAI documents image generation/editing and high-fidelity image inputs for [GPT Image 2](https://developers.openai.com/api/docs/models/gpt-image-2). The built-in image tool used for this review does not expose a model selector; its trials are not evidence that a particular model or snapshot ran. Texture generation belongs in the build/art workflow, never in the gameplay loop. No game API key or runtime image service was added.

Three.js documents a WebGL 2 fallback for WebGPURenderer, but also different custom-material and post-processing requirements and notes that WebGLRenderer can still perform better for some applications. This makes migration a measured experiment for this project. [Three.js migration guidance](https://threejs.org/manual/en/webgpurenderer)

## Review loop

Continue beyond the first attractive screenshot. Each cycle follows: capture → identify the weakest visible issue → estimate its frame/memory cost → implement one coherent change → inspect in motion → benchmark → accept, revise or revert. Repeat at least through materials, silhouettes/poses, and presentation/performance; retain rejected experiments as evidence rather than silently shipping them.

The practical target is sustained 60 FPS on the eventual minimum supported machine (16.7 ms frame budget), with 90–120 FPS where the device/display supports it. For controlled comparisons here, count intervals above 16.9 ms to tolerate timestamp/refresh jitter, also count >33.5 ms and >50 ms intervals, and inspect p95/p99 instead of averages alone. A faster reference machine does not certify slower hardware. A fixed-resolution benchmark also does not validate the entire adaptive-quality controller.

Do not call CPU time GPU time, label a rAF cadence result as GPU headroom, or invent an interactivity score. GPU queries are optional and nonblocking; unavailable/disjoint results must be disclosed. Long tasks help identify responsiveness problems but are not INP or end-to-end input-to-photon latency. Real keyboard/mouse/gamepad interaction and a sustained manual playthrough remain separate checks. A future release target should include browser/device testing and actual Event Timing/INP or an input-latency capture where applicable.

Keep performance mode available, the fixed-step simulation and encounter limits unchanged, and all automated browser tests locked silent. No bloom, depth of field, motion blur, screen-space reflections or other full-screen effect should be added just to lengthen an effects list; an effect must improve gameplay views enough to justify its cost.

## Image-generation trial

Two built-in edits of the original brick were evaluated and rejected. Their opposite-edge RGB error decreased, but the final courses became uneven and the wrap created a wider mortar band. A low numerical edge error is insufficient evidence of seamless masonry. That image is now a fallback; licensed matching brick color/normal/roughness maps replace it on the normal path. Exact rejected prompts and observations remain in [the trial record](../public/assets/brick-weathered-v2.prompt.txt).

Image generation was more useful for the specific missing facial surface. One fictional frontal face was projected onto authored geometry, with calibrated landmarks, skin-palette matching and masks around existing eyes/brows/hair. Front and profile review caused a second blend pass before acceptance. The [asset sidecar](../public/assets/characters/face-albedo-trial.prompt.txt) preserves the exact prompt and remaining source-shading limitations. It is not a scanned face or an independently measured PBR set.
